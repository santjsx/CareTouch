Do not build a “speed dialer.” Build a dedicated communication interface for a person who is effectively non-literate with respect to written UI.

That changes almost every design decision.

The app should not make your mother learn the app. The app should make the phone communicate with her through faces, colors, icons, Telugu speech, sound cues, vibration, and extremely predictable interactions.

There is also one technical constraint you need to accept upfront: normal cellular calling can be made first-class through Android's Telecom APIs, but WhatsApp voice/video calling is controlled by WhatsApp. Your app should not depend on an undocumented mechanism to directly place arbitrary WhatsApp calls. WhatsApp's own documented flow is through WhatsApp's contact/chat/call UI.

Below is the production-grade specification I would use.

12. WhatsApp architecture reality

This needs to be designed honestly.

Your app cannot own WhatsApp's calling infrastructure.

WhatsApp handles its own:

voice calling
video calling
authentication
contacts
call state
network transport
incoming call UI

Your application should therefore act as a launcher/orchestrator.

Conceptually:

Amma App
   │
   ├── Normal call
   │      ↓
   │   Android Telecom
   │
   ├── WhatsApp
   │      ↓
   │   WhatsApp
   │
   └── Voice guidance
          ↓
      Amma App

Don't try to reverse engineer WhatsApp.

That's fragile, potentially policy-problematic, and not production-grade.

WhatsApp's own documentation shows that video calls are initiated inside WhatsApp's calling/chat experience.

13. Normal phone calling

For a simple launcher, Android provides:

ACTION_DIAL

and:

ACTION_CALL

ACTION_DIAL opens the phone app with the number ready; ACTION_CALL places the call directly and requires CALL_PHONE.

For your use case, direct calling is preferable only after explicit configuration and permission, because the entire point is one-tap calling.

But there's another architectural choice.

14. Should this become the default dialer?

Potentially, yes.

If you want a genuinely integrated phone experience, consider implementing Android's:

ROLE_DIALER

That allows the app to become the device's default phone application and implement InCallService. Android's current requirements include handling ACTION_DIAL and providing the required in-call UI.

But don't automatically make it the default dialer in v1.

That's a huge increase in responsibility.

Your first release should be:

Communication launcher + accessibility layer

Then potentially evolve into:

Full default dialer

And one more important point: don't try to achieve “Apple-grade” by adding visual complexity. For this product, Apple-grade means the opposite: ruthless reduction, precise typography, excellent motion, immediate feedback, predictable behavior, accessibility, and almost no cognitive overhead.

The Android platform already gives you the primitives needed for a very polished implementation; the hard part is making the interaction model brutally simple and handling the failure states correctly. Android's current accessibility and performance guidance supports the same direction: large touch targets, semantics, contrast, measurement with Macrobenchmark, and Baseline Profiles for critical flows.

If you build this in Kotlin + Jetpack Compose, I would treat the next deliverable as a full implementation PRD + screen-by-screen UX specification + design system + state machines + permission matrix + Android API mapping + testing matrix + project structure, rather than jumping directly into UI code. That will prevent the usual “beautiful prototype that collapses under real Android edge cases” problem.
